# AmdQuant

A small, inspectable language-model comparison with **AMD Token Factory question normalization and a physical IBM quantum core**. Intended domain: https://amd-quant.com. Repository: https://github.com/uni100h-ops/amd-quant.com.

## What actually runs

1. A visitor asks a question in the web interface.
2. The event's AMD-hosted chat API classifies and normalizes that question into a supported Micro task. This call is shared by both paths. Unsupported tasks stop here, before any IBM submission.
3. Render executes the original classical Micro Transformer on CPU using NumPy.
4. Render executes the hybrid Micro Transformer. At each generation step, its attention and learned projection produce four input angles. The original trained four-qubit RY/CNOT circuit runs on a physical IBM backend. Four measured Z expectations return to the model and influence its next prediction.
5. The interface presents the two answers, timing, normalized question and downloadable provider evidence. AMD does not generate the displayed answer texts. There is no simulator fallback in the deployed hybrid path.

The free API is not a VM for executing our custom PyTorch code, and it does not insert an IBM layer into the provider's large language model. This package deliberately preserves the original Micro checkpoints instead of pretending to modify the hosted model.

## Honest scope

- Two 42,611-parameter models; 311 vocabulary entries; 48-position context.
- Short definitions of supported computing concepts, addition of two single-digit integers, and 12 Spanish-to-English translations.
- The interface supports English, Spanish, French and German. The AMD adapter can normalize French/German input into English. Micro output remains English/Spanish.
- Errors are common outside the training distribution. In local verification, the classical model answered `9.` to `what is 3 plus 4 ?`, but `2.` to `what is 1 plus 1 ?`. A difficult question is not evidence of a quantum speedup.
- Weights were trained with a simulator. Live hybrid inference requires physical IBM measurements. Four logical qubits are mapped onto physical backend qubits by transpilation.
- Same parameter count and output cap do not make the differently trained models a controlled causal ablation. Hardware noise can alter output. No demonstrated quantum speed or general answer-quality advantage.
- Historical Micro/Qwen benchmark downloads use CPU/simulated circuits; they are not the current AMD API + IBM benchmark.
- HyQuT is cited prior work, not our technology or a reproduction: https://arxiv.org/abs/2511.10653.

## Deploy on Render Free

Upload this ZIP's **contents**, retaining folders, directly to the repository root. Do not upload the ZIP itself, credentials, `.env`, `.secrets`, virtual environments or old AMD/Docker deployment files.

Create **New → Blueprint**, select this repository and `render.yaml`. This is one Python **Free** web service. No paid GPU, disk or database is declared. Automatic deployments are off to avoid interrupting IBM work. After subsequent GitHub updates, deploy manually when no comparison is running.

Set these six values in Render's private Environment settings:

| Variable | Source |
| --- | --- |
| `AMD_COMPLETIONS_URL` | The **full inference POST URL** in the event Token Factory API example. The login page is not an API endpoint. |
| `AMD_API_KEY` | The event key once your account is enabled. |
| `AMD_MODEL` | Exact `model` identifier in that API example. |
| `IBM_QUANTUM_API_KEY` | Your existing IBM Quantum API key. |
| `IBM_QUANTUM_INSTANCE` | Your existing instance CRN; it must be **Open Plan**. |
| `IBM_QUANTUM_BACKEND` | An operational physical backend available in that instance. Use `ibm_kingston` only if still available to your account. |

`APP_TOKEN` is generated by the Blueprint for the private diagnostic endpoint. Visitors never enter keys. Other settings are supplied by `render.yaml`.

The AMD adapter targets an **OpenAI-compatible chat-completions API with Bearer authentication**. It sends `model`, `messages`, `temperature`, `max_tokens` and `stream`, and reads `choices[0].message.content`. It does not invoke OpenAI. The event portal's exact URL/model and protocol must be confirmed from its example after access is enabled; they were unavailable when packaging. No successful live Token Factory call is claimed by this release.

Build command: `pip install -r requirements.txt`

Start command: `uvicorn server.main:app --host 0.0.0.0 --port $PORT --workers 1`

Use one worker and one instance: the service serializes physical jobs. For an existing gateway service, remove old `QCHAT_ROLE`, `AMD_API_URL`, `AMD_API_TOKEN`, `QCHAT_DEVICE` and `REQUIRE_AMD` settings and use these commands and variables. There is no separate `api.amd-quant.com` engine.

## Domain

Once the `onrender.com` service works, add `amd-quant.com` in **Settings → Custom Domains**. Copy the exact DNS records from Render into your domain provider and verify the domain. Render supplies HTTPS. Do not redirect the domain to a separate static site: this service hosts both the frontend and `/api/public/*`.

## First verification

- `/healthz` reports process liveness and initialization status; it is not proof of provider execution.
- `/api/public/info` reports configuration readiness. `ready: true` does not mean a QPU job or an AMD inference call has already occurred.
- Run `Translate azul to English` for a short integration test. Confirm that the canonical input is `traduce azul al ingles .`.
- Download the resulting measurement. A completed comparison records `amd.api_call_succeeded: true`, the response ID/model/host, physical IBM job IDs, counts, Z expectations and `consumed_by_model: true`.
- `amd_verified: false` in the model runtime is intentional: Micro runs on Render CPU. AMD participation is the remote API call. The application cannot independently attest the GPU behind an HTTP endpoint.
- Verify IBM job IDs in your IBM dashboard. The app's `physical_quantum_hardware: true` refers to the completed response, not preflight configuration.

## Free-plan operating limits

- Token Factory uses the event's free allowance; availability, expiry and quota depend on the organizer. No unlimited permanent access is promised.
- IBM is restricted to a verified Open Plan instance. The standard allowance is 10 QPU minutes per rolling 28 days, subject to IBM promotions/terms. Queue wait is not that usage metric. The app uses ordinary jobs, not paid sessions.
- Default: 1 comparison at a time, 16 output steps per model, 1,024 shots per IBM job, 32 IBM submissions per UTC day, 60 seconds maximum QPU execution per job, one hour wait per job and two hours per comparison. These limits can yield a partial or failed response; they cannot remove provider queues.
- Render Free can sleep after inactivity or restart at any time, losing SQLite state and results. Keep the page open during a comparison and download its result. This cannot guarantee uninterrupted execution.
- Before new requests, the app checks outstanding tagged IBM jobs and previous request IDs. It also checks provider history before each submission, so deleting local state does not simply reset the daily IBM budget. It never automatically repeats an ambiguous submission.
- A restart does **not** resume the missing Micro generation context. A remaining IBM job may need to finish or be cancelled in the IBM dashboard before new work. Known locally recorded jobs are cancelled during recovery. Unknown provider state blocks submission.
- Use only one deployment with these credentials/tags. Do not run the previous local test script or another deployment concurrently; a provider quota check is not a distributed lock.
- Render's free instance hours are shared with your other free services in the workspace. Bandwidth/build allowances also apply. Domain registration is separate. If you need durable history, an optional paid Render instance plus disk is described in the owner's guide; it is not selected here.

## Validation of this release

Local tests cover NumPy/Torch numerical and generated-output parity with the original checkpoints, physical-core callback dependence, shared AMD normalization, provider failures, no simulation fallback, restart/history guards, quota checks, API secret boundaries and the four-language UI. Provider calls in these tests are mocks; reference statevector calculations are test-only and are not included in this ZIP. No actual AMD key or IBM credentials were used by the packager.

The original CPU + IBM test supplied by the project owner is evidence for the earlier route; it does not verify this new Token Factory + Render deployment. A live end-to-end run remains necessary after configuration.
